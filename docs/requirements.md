> **本ドキュメントについて**：この要件定義書は、開発時にClaude Codeへ渡して実装を進めるための仕様書を兼ねています。実装時は各章の決定事項に従い、第15章「更新履歴」が最新の変更内容です。第14章「今後の検討事項」は未確定のため、実装時に判断が必要な場合はユーザー（Shoki）に確認してください。

## 1. プロジェクト概要

**Sporive** は、理想の体づくりに向けて、AIによるパーソナライズされたトレーニング計画を提案するPWA（Progressive Web App）。
若者からシニアまで幅広い層を対象とし、シニア層には筋力維持・向上を主眼とした提案を行う。
継続的なモチベーション維持のため、進捗の可視化・通知機能・連続達成記録・負債管理（未達成分のリカバリー）を実装する。

- **デモ版**：2026年7月末目標
- **試験運用**：2026年8月〜
- **コスト方針**：すべて無料プラン内で運用
- **ドメイン**：購入なし。Vercelのデフォルト無料サブドメイン（`xxx.vercel.app`）を使用

---

## 2. 対象ユーザー

- 若者〜シニアまで幅広い年齢層
- シニア層には筋力維持・向上を重視した低強度中心の提案を行う
- 利用者側の画面は**スマホ専用**。スマホ以外でアクセスした場合はスマホで開くよう促す画面を表示
- 管理者画面は**PC・タブレット専用**

## 3. 技術構成

| 項目 | 選定技術 | 補足 |

| フロントエンド | Next.js（PWA対応） | フロントとサーバー処理（API Routes）を一元化 |
| ホスティング | Vercel（無料プラン） | 軽量構成を目指す |
| AI | Google Gemini API（Google AI Studio） | 無料枠内で運用。トレーニング計画の提案に使用。使用モデル：`gemini-3.5-flash-lite`（環境変数で変更可能） |

| カレンダー連携 | Google Calendar API（OAuth2） | 提案とカレンダー追加の両方に使用（詳細は6章） |

| アクセス解析 | Google Tag Manager（GTM）経由でGoogle Analytics（GA4）を計測 | 無料枠内で運用（詳細は13章） |
| サイト検証 | Google Search Console（HTMLタグ方式で所有権確認） | 詳細は13章 |

- Firebase：AI・通知含め当初検討したが、DBにSupabaseを選定したためベンダー統一の観点で通知もFirebase不使用の素のWeb Push APIに変更

## 4. アカウント・認証機能

- **アカウント作成時**：Googleアカウント認証（OAuth）を実施
- OAuth認証後、同じメールアドレスに対して**パスワードを設定**する画面を表示
- **ログイン時**：Google OAuthログイン、またはメールアドレス＋パスワードログインのどちらも可能（Supabase Authのアイデンティティ連携機能を利用）
- アカウント作成時に**Googleカレンダーへのアクセス許可**を求める
- 大量アカウント作成対策：新規登録がGoogle OAuthのみ（メール/パスワード単体での新規登録フォームは存在しない）のため、Googleの認証自体がゲートとなり実質的に抑制済みと判断。追加対策は見送り
- 実装タイミング：**7月デモ版でここまで実装**

### 4-1. 認証セキュリティ強化（計画）

- **JWT（アクセストークン）有効期限**：Supabaseのデフォルト（3600秒）から**1800秒（30分）**に短縮（Supabase Dashboard設定）
- **リフレッシュトークンローテーション**：有効化する。使用済みのリフレッシュトークンが再度使われた場合（漏洩・不正利用の兆候）、該当セッションを強制失効させる再利用検知もあわせて有効になる（Supabase Dashboard設定）
- **Auth Rate Limits**：ブルートフォース対策として、サインイン試行の制限を強化（Supabase Dashboard設定）
- **CAPTCHA**：Cloudflare Turnstileを採用（無料枠の制約がないため、hCaptchaより優先。利用にはTurnstileのアカウント登録が必要）
- **カスタムSMTP**：Resendを採用。Supabase既定のメール送信は1時間あたり数通に制限されており本番運用に不向きなため（Resend無料枠：3,000通/月・100通/日）
- **メールテンプレートの日本語化**：パスワード再設定・確認メール等をSupabase標準の英語から日本語に変更
- **MFA（多要素認証）**：TOTP（認証アプリ）方式のみ採用。全プランで無料。電話番号によるAdvanced MFA Phoneは有料（$75/月〜＋SMS従量課金）のため不採用
- **カスタムアクセストークンフック**：Postgres関数としてAuth Hookを実装し、JWTクレームに`is_admin`・`is_super_admin`を埋め込む。管理者判定のたびに発生していたDB往復を削減するとともに、10-3「高度な設定」のsuper-admin判定に用いる
- **ログイン中の端末一覧・全ログアウト**：Supabase側のセッション一覧取得APIで実現可能か要検証。検証結果次第で仕様を確定する

## 5. AIによるトレーニング計画提案機能

- 利用者の目標（自由記述でプロフィール登録・設定画面から入力。入力文はGemini APIで簡潔な文章に整形してから保存）とスケジュールに基づき、Gemini APIでパーソナライズされたトレーニング計画を提案
- スケジュール編集画面のAI提案時には、プロフィールの目標とは別に「今回の要望」を自由記述（任意、最大300文字）で追加入力可能。プロフィールの目標に加えて優先的に反映され、保存はされず提案生成の都度の一時的な入力として扱う
- 利用者が自分でトレーニング計画を設定することも可能
- 利用者が計画の「登録」ボタンを押した際に、AIが改善案を提示する機能を搭載
- 週単位（1週間）でのトレーニングスケジュールを作成
- 週間AI提案・AI改善提案・リカバリー提案（§7）・目標の自由記述要約は、管理者の「高度な設定」画面（§10-3）の「AI機能」マスタースイッチで一括停止、または機能ごとに個別停止できる（計画。Gemini API障害・混雑時の一時停止を想定）

### 5-1. 運動強度の妥当性検証機能

AIが提案する運動強度が妥当かどうかをアプリ内でチェックする機能。

- **判定方式**：ルールベース（数値条件による事前定義の閾値チェック）
  - 理由：API消費量を増やさない、判定が即時、判定理由を利用者に明示できる
  - 将来、既往症・ケガの自己申告など自然言語での複雑な判定が必要になった場合は、AIによるダブルチェックの追加を検討
- **判定基準**：
  - 年齢層別の上限（シニアは低強度中心など）
  - 進行方式（週あたりの重量・回数の増加率に上限を設定し、過度な負荷増加を防止）
- **実装タイミング**：8月試験運用以降に追加（7月デモには含めない）
- ルールベース判定でありAI（Gemini）を使用しないため、「高度な設定」の機能フラグ（§10-3）では「AI機能」とは独立した「運動強度チェック」フラグで制御する（計画）

## 8. 通知機能

- **実装方式**：Web Push（VAPID、素のPush API）。Supabase pg_cron + pg_net で送信トリガーを管理（第15章の更新履歴を参照）
- 通知設定は`/settings/account/notifications`（アカウント設定配下）に統一する
- お知らせ履歴へのショートカットは**headerに常時固定表示**（ベルアイコン）

### 8-1. 通知種別（計画：種別ごとに時刻・ON/OFF可否を分離）

| 種別 | 既定時刻 | 時刻変更 | ON/OFF変更 | 既定 |
|---|---|---|---|---|
| 当日予定通知 | 08:00 | 可 | 不可（常時有効） | 有効 |
| 負債リマインダー | 20:00 | 可 | 不可（常時有効） | 有効 |
| 再エンゲージメント通知（新規。3日以上トレーニング記録がない利用者へ送信） | 17:00固定 | 不可 | 可 | 有効 |
| 週次レポート（新規。Geminiで週間の振り返りを生成して送信） | 毎週日曜・時刻は利用者指定 | 可 | 可 | 無効 |

- 通知時刻の入力は10分刻み。実際の配信判定はpg_cronジョブ（10分おき）で行うため、指定時刻から最大約10分の遅延が生じ得ることを設定画面に明記する
- **非通知時間帯・非通知曜日**：利用者ごとに設定可能（計画）。該当する時間帯・曜日に該当する通知はスキップし、後追い送信はしない
- タイムゾーンは日本時間（Asia/Tokyo）固定とし、利用者ごとのタイムゾーン設定機能は作らない

### 8-2. データ保持・定期クリーンアップ（計画）

- プッシュ通知履歴（`notification_logs`）は**30日**を超えたものをpg_cronで定期削除する
- 期限切れの`push_subscriptions`も同ジョブで削除する
- クリーンアップジョブはVercel APIを経由せず、Supabase内部でSQLのみで完結させる
- 実行タイミングは8-3のメンテナンスタイム内（3:00開始）

### 8-3. 定期メンテナンスモード（計画）

サイト全体を対象とした、日次の定期メンテナンス体制。目的はメンテナンスタイム中にSupabaseへの書き込みを止め、定期クリーンアップジョブ（8-2）に専念させること。

| 時間帯（JST） | 状態 |
|---|---|
| 1:00〜2:30 | 通常利用可能。全画面上部に「まもなくメンテナンスです」のお知らせバーを表示 |
| 2:30〜3:30 | メンテナンスタイム。トップページ（`/`）以外へのアクセス不可（ログイン中の利用者も含む）。ログイン試行時は「ただいまサイトメンテナンス中です」と表示 |

- **例外**：管理者画面（`/admin`配下）はメンテナンスタイム中も通常通り動作する
- 定期メンテナンス予告のお知らせバーは、10-3「高度な設定」の「お知らせ」機能に統合し、システムが自動投入する定期お知らせとして扱う
- 上記の日次スケジュールとは別に、super-admin権限を持つ管理者が任意のタイミングで即座にサイト全体をメンテナンス状態にできる「緊急メンテナンスモード」を機能フラグ（§10-3）として用意する

### 8-4. お知らせ履歴画面

- `/settings/notifications`は**「お知らせ」画面**に改名する（旧称：通知履歴）
- 画面内に「通知履歴」「お知らせ」の横並び切替ボタンを設置し、表示を切り替える
  - **通知履歴タブ**：送信済みプッシュ通知の履歴（`notification_logs`、直近30日分）
  - **お知らせタブ**：管理者が発行したお知らせ（10-3参照）の一覧。タイトルのみ表示し、未読には「新規」バッジを表示。タップするとタイトル・本文が全画面表示になり、その時点で利用者ごとに既読化する

## 10. 管理者画面

### 10-1. アナリティクスダッシュボード

利用者の統計・アナリティクスを表示。開発者自身がプロジェクト発表時に活用できる見せ方も意識する。

- 利用者数・継続率などの基本指標（DAU/WAU、リテンション）
- 負債発生率・達成率などのトレーニング系KPI
- AI提案内容の分析（人気メニューなど）
- プロジェクト成果を示せる指標（利用者数の推移、継続率の変化、負債解消率など）

### 10-2. 管理者権限の区分（計画）

- **is_admin**（既存）：アナリティクスダッシュボード等、通常の管理者画面へのアクセス権
- **is_super_admin**（新設）：上記に加え、10-3「高度な設定」へのアクセス権を持つ上位権限
- カスタムアクセストークンフック（§4-1）でJWTクレームに両フラグを埋め込み、判定に用いる

### 10-3. 高度な設定（計画）

`is_super_admin`を持つ管理者のみメニュー表示・アクセス可能な設定画面。「機能」「お知らせ」の2タブで構成する。

**機能タブ**：サイト機能の一括ON/OFFトグル

| フラグ | 内容 |
|---|---|
| AI機能（マスタースイッチ） | 週間AI提案・AI改善提案・リカバリー提案・目標の自由記述要約を一括制御。各機能も個別にON/OFF可能 |
| 運動強度チェック | ルールベース判定（§5-1）のためAI機能とは独立 |
| 新規ユーザー登録 | `/signup`の受付停止 |
| 通知機能全体 | プッシュ通知の送信を一括停止 |
| Googleカレンダー連携 | カレンダー連携機能を一時停止 |
| 緊急メンテナンスモード | super-adminが任意のタイミングで即座にサイト全体をメンテナンス状態にできる手動スイッチ（§8-3参照） |
| 負債管理機能 | 負債の記録・リマインダー・補填提案を一時停止 |

上記に加え、ログイン機能停止・パスワードログイン停止（Google OAuthのみに制限）・アカウント削除機能停止・管理画面エクスポート機能停止・進捗記録機能停止を追加候補として検討中（優先度・要否は実装時に確定）。

**お知らせタブ**：サイト全体向けのお知らせバー・お知らせ履歴（§8-4）を作成・管理する機能

- 入力項目：タイトル・本文・レベル
- **レベル**（3段階、専用CSSで色分け表示）

  | レベル | 用途 | 表示色 |
  |---|---|---|
  | お知らせ | 新機能案内・定期メンテナンス予告など通常の告知 | ネイビー（基調色） |
  | 注意 | 一部機能に影響する軽微な不具合・一時的な制限など | ティール（`accent-teal`） |
  | 警告 | 障害・緊急メンテナンス・重要な対応依頼など | コーラル（`accent-coral`） |

- **お知らせ・注意レベル**：影響範囲ページを選択可能（選択したページ名がお知らせ本文の下部に表示される。情報提供のみで機能制限はしない）
- **警告レベル**：開けなくするページを選択可能（選択したページは警告が有効な間、実際にアクセス不可になる）
- 定期メンテナンス予告（§8-3、1:00〜2:30のバー）は、この仕組みの中でシステムが自動投入する定期お知らせとして扱う
- ページの選択肢：ホーム・スケジュール・進捗・負債管理・お知らせ・アカウント設定・すべて

## 13. SEO・アクセス解析

### 13-1. 検索エンジン最適化（SEO）
- 認証必須ページ（ログイン後のみアクセスするページ）は`robots: { index: false, follow: false }`でnoindex。公開ページ（トップ・利用規約・プライバシーポリシー・ログイン・新規登録）のみ検索エンジンに公開する
- `robots.txt`・`sitemap.xml`をNext.jsのMetadata Route機能で生成し、Search Consoleに送信する
- 各公開ページにOGP・Twitter Card用の1200×630画像を自動生成する（アプリのアイコンデザインを反映）
- トップページに構造化データ（JSON-LD、SoftwareApplication schema）を追加する
- HTTPセキュリティヘッダー（`X-Content-Type-Options`・`X-Frame-Options`・`Referrer-Policy`・`Permissions-Policy`）を追加する

### 13-2. Google Search Console
- サイト所有権確認は「HTMLタグ」方式（`<meta name="google-site-verification">`）を採用する
  - 当初「Google タグ マネージャー」方式を検討したが、Next.js App RouterではGTMスニペットの厳密な設置要件（`<head>`直下への設置・`<body>`直後にコメント以外を挟まないこと）を満たせないため断念した
- **既知の制約**：`sporive.vercel.app`はVercelの無料共有サブドメインであり、Googleはこうした共有サブドメインのクロール優先度を下げる傾向がある。そのためSearch Console上でサイトマップが正しく読み込まれるまで時間がかかる場合がある（サーバー側の応答自体は正しいことを確認済み）。恒久対応は§14「今後の検討事項」の独自ドメイン取得を参照

### 13-3. アクセス解析
- Google Tag Manager（GTM）経由でGoogle Analytics（GA4）を計測する
- SPA（クライアントサイド遷移）のため、ルート変更時に`dataLayer.push({ event: "page_view", ... })`でカスタムイベントを送信し、GTM側のトリガーでページビューを計測する
